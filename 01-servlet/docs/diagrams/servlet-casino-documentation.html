1. Overview

The application is a small casino with a slot machine. It is built from three servlet-based services. Each one is deployed in a different application server and they communicate with each other over HTTP, like small microservices.

ServiceServerPortURLRole
ui-serviceTomcat 118080/uiThe only service used by the browser. Servlets and JSP pages, user session, calls the other two services.
wallet-serviceJetty 12.18081/walletHolds the chip balance of each player (debit / credit).
games-serviceWildFly 428082/gamesSlot machine logic: draws the reels and computes the payout.

All three run at the same time, as Docker containers, and the WAR files are copied manually into each server (not deployed from an IDE). The technologies are Java 25, Jakarta Servlet 6.1 (Jakarta EE 11), JSP with EL, Maven (WAR packaging) and Gson (JSON parsing in ui-service only).

2. Theoretical aspects and solution adopted

  • Servlet: a Java class, extending HttpServlet, that handles HTTP requests inside a servlet container. Lifecycle: the container creates it, calls init() once, then doGet / doPost for each request (on many threads), and destroy() at shutdown.
  • WAR and context path: a web application is packed as a .war file. The file name gives the context path (ui.war is served at /ui). Routes are declared in WEB-INF/web.xml (servlet name, class, url-pattern).
  • WEB-INF: a directory defined by the Servlet specification that the server never serves directly. The JSP views are kept there, so they can only be reached through a servlet with RequestDispatcher.forward.
  • Forward vs redirect: forward passes the same request to a JSP inside the server (URL unchanged, request attributes kept). sendRedirect makes the browser send a new request (used after a successful POST).
  • Session: HttpSession keeps the logged-in username between requests of the same browser (30 minutes timeout).
  • Communication: the services call each other with plain HTTP (java.net.http.HttpClient). Requests carry application/x-www-form-urlencoded parameters, answers are JSON. No token is needed because only ui-service is reachable from the browser.
  • Layered design (in every service): web (servlets, HTTP only) → application (service with the use cases, DTOs) → domain (entities, exceptions, interfaces) ← infrastructure (implementations of the interfaces). The domain defines interfaces (WalletClient, AccountRepository, SymbolSource) and the infrastructure implements them, so storage or HTTP details can be changed without touching the business rules.
  • Alternatives (not implemented): message queues (JMS / RabbitMQ) instead of direct HTTP calls, so services would not need to be online at the same time; JSON request bodies or JAX-RS instead of form parameters; a database for the balances; a token (JWT) between services; all code in a single WAR on one server.

3. Architecture

Deployment. docker-compose.yml starts the three containers. Inside Docker every server listens on 8080 and a different port is mapped on the host. Containers reach each other by service name (http://jetty:8080/wallet, http://wildfly:8080/games), not by localhost. The two addresses are passed to ui-service through the environment variables WALLET_URL and GAMES_URL (defaults: localhost:8081 and localhost:8082).

Only prototypes are given (name, parameters, return type, exceptions). Exceptions are unchecked (RuntimeException) unless noted. Getters and private helpers are omitted.

5.1 wallet-service (package casino.wallet)

web.WalletServlet extends HttpServlet - HTTP entry point; translates HTTP to WalletService calls and writes JSON. It contains no business rules. It maps AccountNotFoundException to 404, InsufficientFundsException to 409 and IllegalArgumentException to 400.

void init()
void doGet(HttpServletRequest req,
           HttpServletResponse resp) throws IOException
void doPost(HttpServletRequest req,
            HttpServletResponse resp) throws IOException

init() runs once and creates the layers: new WalletService(new InMemoryAccountRepository()). doGet and doPost read the path (getPathInfo()) and the parameters username / amount.

application.WalletService - the business rules. Its methods are synchronized, so "read balance, check, write balance" cannot be interleaved by two requests.

WalletService(AccountRepository repository)
AccountDto createOrGet(String username)
AccountDto get(String username)
    throws AccountNotFoundException
AccountDto debit(String username, long amount)
    throws AccountNotFoundException, InsufficientFundsException
AccountDto credit(String username, long amount)
    throws AccountNotFoundException
// createOrGet: existing account, or new one with 1000 chips
// all methods: IllegalArgumentException if username is blank or
// longer than 30, or amount <= 0

domain - Account (record: String username, long balance, immutable; Account withBalance(long newBalance) returns a copy), AccountRepository (interface), AccountNotFoundException(String username), InsufficientFundsException(long balance, long amount).

interface AccountRepository {
    Optional<Account> findByUsername(String username);
    Account save(Account account);   // insert or replace
}

infrastructure.InMemoryAccountRepository implements AccountRepository - accounts are stored in a ConcurrentHashMap; data is lost at restart. application.AccountDto is a record (String username, long balance) given to the servlet.

5.3 ui-service (package casino.ui)

web.AppContextListener implements ServletContextListener - runs once when the application starts.

void contextInitialized(ServletContextEvent event)

It reads WALLET_URL and GAMES_URL, builds one CasinoService and stores it in the ServletContext under the key CASINO_SERVICE = "casinoService". Each servlet takes it in init().

web.LoginServlet, web.PlayServlet, web.LogoutServlet extend HttpServlet (routes /login, /play, /logout, declared in web.xml).

LoginServlet, PlayServlet:
  void init()
  void doGet(HttpServletRequest req, HttpServletResponse resp)
      throws ServletException, IOException
  void doPost(HttpServletRequest req, HttpServletResponse resp)
      throws ServletException, IOException
LogoutServlet:
  void doPost(HttpServletRequest req, HttpServletResponse resp)
      throws IOException

LoginServlet validates the user through CasinoService.login, stores username in the session and redirects to /play. PlayServlet checks the session, calls getAccount or play, and forwards to play.jsp or result.jsp with request attributes (account, result, error). If the account no longer exists (HTTP 404 from the wallet), the session is invalidated and the user returns to login. The views are WEB-INF/jsp/login.jsp, play.jsp, result.jsp (values are shown with EL, e.g. ${account.balance}), plus the public style.css.

    Account credit(String username, long amount);
}

exceptions (each with a String message constructor):
    AccountNotFoundException, InsufficientFundsException,

infrastructure - HTTP implementations:

HttpWalletClient(String baseUrl)    // implements WalletClient
HttpGamesClient(String baseUrl)     // implements GamesClient
HttpJsonClient(String serviceName, String baseUrl)
    JsonResponse get(String path)
    JsonResponse post(String path, Map<String,String> form)
    // both throw ServiceUnavailableException

    JsonObject json()

HttpJsonClient uses java.net.http.HttpClient (connect timeout 3 s, request timeout 5 s). If the other service cannot be reached it throws ServiceUnavailableException("Wallet service is not reachable"), which the servlet shows as a message instead of crashing. The Http*Client classes translate HTTP status codes into exceptions: 400 → IllegalArgumentException, 404 → AccountNotFoundException, 409 → InsufficientFundsException, anything else → ServiceUnavailableException. DTOs for the JSPs: AccountDto(String username, long balance) and PlayResultDto(List<String> reels, long bet, long payout, boolean win, long balance).

6. Processing flow

Login. Browser → POST /ui/login → LoginServlet → CasinoService.login (validates the name) → POST wallet/api/accounts (creates the account with 1000 chips, or returns the existing one) → username saved in the session → redirect to /play.

Play (CasinoService.play):

  1. wallet: debit the bet. If the balance is too low (409) the flow stops with an error message.
  2. games: spin with the bet and get the reels and the payout.
  3. If the games call fails, the bet is given back with a wallet credit (compensation) and the error is shown.
  4. If the payout is greater than 0, wallet: credit the payout.
  5. The servlet forwards to result.jsp with the reels, payout and the new balance.

7. Context of use

  • Requirements: Docker Desktop (to run the three servers), JDK 25 and Maven (only to rebuild the WARs), PowerShell for the build scripts.
  • Server images: tomcat:11.0-jdk25, jetty:12.1-jdk25 (with the ee11-deploy module), quay.io/wildfly/wildfly:42.0.0.Final-jdk25. All support Jakarta Servlet 6.1.
  • Limits: balances are kept in memory and reset when wallet-service restarts; there is no password (a username is enough); ui-service must be able to reach the other two by network.

Build and run (from 01-servlet/deploy):

.\tools\build-all.ps1          # builds the 3 WARs, copies them to the server folders
docker compose up -d --build   # starts Tomcat, Jetty and WildFly
docker compose ps              # all three must be "Up"
docker compose down            # stop
